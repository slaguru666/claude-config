## 2026-09-13 — one sanitiser, two hosts, and a note you can write

Slice 2 of the standalone Corkboard. A note body is now decided in one place,
`src/data/sanitize.mjs`, and both hosts use it. Head `3603140`, pushed. Record
in `docs/verification/2026-09-13-standalone-slice-2.md`.

- **Two tiers, not one.** `ingest` says what may be stored, `display` says what
  is drawn, and they are deliberately different sets — a table written in
  Foundry is legal but undrawn, so it survives a trip through the app instead of
  being quietly deleted by it. Conflating them is what would make a
  Foundry → iPad → Foundry round trip lossy.
- **Tokenise and rebuild, never strip.** Both tiers parse the input and write a
  fresh document from the parse with everything escaped. A sanitiser that edits
  its input hands the browser bytes it never fully parsed, and the gap between
  what it thought it read and what the parser decides those bytes mean is where
  the whole mutation-XSS genre lives.
- **Both hosts moved off `foundry.utils.cleanHTML`.** A source-level guard in
  the suite keeps it that way. The display tier is narrower than core's — tables
  and images in a Foundry note now draw as text — which is the contract's call,
  not a regression: what is drawn is exactly what the editor can offer back.

## 2026-09-13 — pictures, stored once

Slice 3 of the standalone Corkboard. A picture is stored under `asset:` and the
SHA-256 of its bytes, and the URL a browser can load is made at draw time and
revoked when the screen goes. Head `69238ab`, pushed, 1090 tests. Record in
`docs/verification/2026-09-13-standalone-slice-3.md`.

- **Resolution is a seam, not a step.** `mountBoard` and `applySurface` take a
  resolver; a host that supplies none is one whose references are already URLs,
  which is Foundry. A `blob:` URL is valid only for the document that made it, so
  one in a saved board is a dangling reference the moment the page reloads.
- **Reclaiming scans the snapshots AND the commits.** A board is rebuilt by
  replaying its log, so bytes only an old commit names are bytes a replay will
  ask for. The practical effect is that a picture goes when the board goes, not
  when the card does — which is the right way round, because removing a card is
  something people undo.
- **The sweep was blind to every board on the device, and the tests agreed with
  it.** It read a field off the `boards` row that does not exist — that row is
  metadata; a board's content is a snapshot plus the commits after it — and the
  fixtures had invented the same shape. Found by dumping real IndexedDB records
  during the live run. The faithful storage fake now lives in
  `test/helpers/fake-idb.mjs` so there is one of it, and fixtures build boards
  through `BoardStore` rather than by hand.
- Tim asked whether this could become a shared server app. Answered: it is
  already phases 5–6 of the design, the commit is already the transaction, and
  the real missing piece is per-entity preconditions — not the socket.

- **2026-09-15** — Corkboard: rebuilt the coupling boundary (1488f9a) after
  three failed fixes at the same place. [[corkboard]]

**The pattern was the diagnosis.** Reviews 32 and 33 found four defects between
them, and every one was the same mistake wearing a different size: the policy had
TWO key shapes to reason about, `shapes.<id>.<field>` and `shapes.<id>`, and kept
inferring from the shape of a key things the key does not say — whether the entry
is a line, whether it names its whole group, whether the members it does not
mention are meant to change. Each fix was correct about the case in front of it
and wrong one level down. Key shape, then field granularity, then object
granularity.

So the fix was to delete the second key shape rather than write a fourth rule for
it. A write of a whole entry is rewritten as writes of the fields it sets, which
is the *same write* — Foundry merges an object into an existing entry rather than
replacing it. Afterwards there is one kind of key and no case analysis, and both
of review 33's findings stop being cases to handle: a restored card is no longer
an all-or-nothing blob, and a partial import stops looking complete because it
stops being a whole entry.

The scoping rule that keeps it small: **flattening is the price of turning
diffing off, so it is paid only where diffing is turned off.** An uncoupled write
is handed back exactly as built. A creation stays whole, because an absent entry
cannot be addressed a field at a time.

**Two guards, and what testing them found.** Two mutants survived the sweep —
both guards that no current producer can trigger. Rather than delete them as dead
code or leave them untested, I wrote tests that hit them directly: `Object.entries`
of a string yields its characters, and a flattened deletion would resurrect what
it deletes. Writing those found a third defect nobody had reported —
`thinUncoupled` folded the `-=` away and so compared a removal against the entry
it removes. Today's removals carry null and always differ, so nothing was broken;
the rule was wrong regardless. A guard worth keeping is worth a test that reaches
it without a producer.

## 2026-09-15 — load testing: bandwidth binds first, and commits have no brake

Measured in three places rather than one, because no single vantage point could
answer it: the service in-process over real sockets (its own CPU cost, fake
store), **real Postgres over loopback on the box** against `corkboard_test`, and
proxy+TLS from outside.

**The headline is bandwidth, not CPU.** Fan-out sends the whole board to every
recipient, so cost is O(watchers × board size): **4.89 MB per commit** at 32
watchers on a 300-card board. Five commits a second is ~25 MB/s of egress. The
uplink gives out long before anything else does.

**Postgres is the floor on latency**: 8 ms per commit at 10 cards, 17 ms at 300,
loopback. So 60–120 commits/s per board before fan-out. `changesSince` is flat at
~1 ms across sizes, so the `order by base` index earns its keep.

**And this retires an open question about the retry.** In-process against the fake
store it absorbed 16-of-16 concurrent commits with nothing refused; production gave
7/1 and 6/2. Not variance in the feature — the fake resolves a write in ~1 ms and
Postgres in 8–17, so the contention window is an order of magnitude longer in
production. **Any in-process concurrency result is optimistic, and now by a known
factor.** The same-card floor held everywhere: exactly one winner at 8 and at 32.

**The real finding a load test exists to produce: there is no rate limit on
commits.** Login is throttled, SSE connections are capped (`perUser` 8, `perBoard`
32), and the write path has nothing. One authenticated writer can commit as fast as
it can loop, and every commit bills every watcher a whole board.

**My own harness lied first, and the rows caught it.** Rows for 8, 16 and 32
watchers came back *identical* — 454 commits/s, 800 events, 25.0 MB. That plateau
was `perUser: 8`: every watcher used one account, so the 9th onward got 429 and I
measured 8 watchers three times while labelling them 8, 16 and 32. The harness had
counted the refusals and I had not printed them. It now creates an account per
eight streams and **throws rather than reporting an audience it did not achieve.**

Second instrument failure, same run: the first Postgres numbers were taken through
an SSH tunnel from the Mac — 32 ms to read a 10-card board — which is round-trip
latency, not the database, and nothing the service ever pays. Re-run on the box over
loopback the same read is 1.7 ms. **A measurement taken through a tunnel measures
the tunnel.**

Not run, deliberately: a heavy end-to-end run against production. The box also
serves live Foundry VTT v13, a publish endpoint and filebrowser, and with no commit
rate limit a real load test could degrade services nobody asked me to touch. Flagged
to Tim rather than decided.

  `dist-v2` and `dist-phone` are tracked, and a cone without `pwa` would have git delete

## 2026-09-15 — the commit brake, built: it slows, it does not refuse

`d46223a`, to the spec in `7bb8edd`. The whole design turns on one fact found by
reading the client rather than the server: **refusing a commit destroys work.**
`WebSession.commit` returns false, the card springs back, and the person is told
their change was not saved. `throttle.mjs` chose a delay for logins because a
lockout locks people out of their own accounts; here it is sharper — the person did
nothing wrong. So over-budget commits are held and then processed, and the refusal
past the cap exists only because a request held for ever is its own denial of
service.

The client half was not optional and would have been easy to skip: `#why` had no
case for this, so a 429 read "That change did not make sense to the board, so
nothing was saved" — blaming the content and declaring the work lost, both wrong.
A `too-fast` answer is now retried once, honouring `Retry-After`, and a successful
retry says **nothing**. A 409 is deliberately not retried.

**The sweep earned its keep twice, which is the part worth remembering.** 12/12
caught, but only after it found two things I would have shipped:

- **A tautology.** My burst test asserted that `COMMIT_RATE.perBoard.burst`
  commits are free — true for any value, including 2. And the sustained test could
  not catch a shrunken *rate*, because ten seconds never exhausts the bucket. Both
  now pin **literals**: thirty in an instant, three a second for a solid minute.
  **A test that reads its expectation from the code under test asserts nothing.**
- **A hang in my own test.** `while (!brake.take(keys).refuse)` spins for ever
  against any mutant that never refuses, and being synchronous it starves the event
  loop — so vitest's own testTimeout cannot fire and the run HANGS rather than
  fails. That is the same starvation that argued for bounding the commit retry this
  morning, met again in a test, and it cost two stalled sweep runs before I
  recognised it. Bounded now, with the reason beside it.

Not deployed. The numbers (5 commits/s per board, burst 40) are judgements set from
what a body can physically do, not from observed traffic — the honest caveat is in
the spec's open decisions. Byte budget deliberately not enforced: bytes are the
faithful unit but cannot be chosen without real board sizes, so log first.

### 2026-09-15 — reconnect after a drop: it works, then it doesn't, and the comment defends the wrong case

The last open question from the SSE work, tested on production with a real
browser. It found a defect, which is the point of testing the thing nobody had.

**Short drop: perfect.** A ~1s `systemctl restart` resets the connection without
an HTTP response, so the browser sees a network error, retries, reconnects, and
is caught up by the whole-board open event. A commit made *while the page had no
connection* appeared with no reload — one navigation, document alive 63 seconds —
and the reconnected stream then carried further live pushes, so it is a working
stream and not a zombie. That is the recovery mechanism from
`test/web-recovery.test.mjs` proved end to end through nginx.

**Long drop: never recovers.** Stop the service for ~48s and the retry reaches
nginx while the backend is down, so nginx answers **502 with an HTML body**. Per
the EventSource spec, any response that is not 200 + `text/event-stream` is a
PERMANENT failure — the browser closes the stream and does not retry. The page
then sat three revisions behind indefinitely, with **no banner and nothing on
screen to say so**. A reload fixed it at once, proving the page was fine and only
the stream was dead.

**The comment is the lesson.** `session.mjs:227` installs no `error` handler on
purpose, because "closing here would turn a thirty-second wifi drop into a board
that is quietly stale until somebody reloads". That is correct about a WIFI drop
— a network error, which the browser retries — and wrong about a SERVER drop
behind a proxy, which is a 502 and is not retried. The comment defends one of the
two cases and the other delivers exactly the outcome it was written to prevent.
**Every deploy is the case it does not cover.** Same shape as
[[feedback-guarantee-not-argument]]: sound reasoning, wrong subject.

**My own instrument lied again, in the same test.** I asked whether anything on
screen said the board was stale; the check came back TRUE. It had matched the
board's own name — I had called it "reconnect after a drop". Printing the matched
words showed a single hit, `reconnect`, in the title. The honest answer was no
banner at all. A regex over `innerText` is an extractor, and an extractor that
can match your own fixture is not measuring the page.

### 2026-09-15 — the dead-stream fix, and a survivor that was the real find

`463b7a1`. Committed, not deployed. Fixes the defect found an hour earlier by
actually testing reconnect-after-a-drop on production.

**The shape of the fix is "supply only what the browser withholds".** It acts on
`readyState === CLOSED` and does nothing otherwise, because a second stream
racing a live one is worse than the drop it is trying to fix. A fake with no
`readyState` reads as "not closed", which is why the existing leave-it-alone test
passes unchanged — the new behaviour is additive rather than a reversal.

**"Back" is a board arriving, not a socket opening.** The server sends the whole
board on every connection, so the first `board` event is the moment the client is
genuinely caught up; an `open` followed by nothing would otherwise be reported as
recovery. That is the property `test/web-recovery.test.mjs` already holds, reused
rather than re-asserted.

**The sweep's thirteenth mutant was a survivor.** Nothing held the guard against
scheduling a reopen on top of a pending one, so a stream reporting its death
twice — an `error` listener is not promised to fire once — would have doubled its
streams on every failure, which is the opposite of a backoff. Twelve
confirmations of tests I wrote deliberately were worth less than the one that
found a hole. Second time today (the other was `pin.cache.img` in the collector).

**Also removed the refuted belief from the test that carried it.** The old test
was named "does NOT close the stream on an error, BECAUSE EventSource reconnects
itself" — a name asserting the half-truth that caused the bug. Renamed to what it
actually checks and told where the other half lives. This morning's lesson
applied without being prompted: a correction is not landed until a grep for the
old claim comes back empty, and a test name is a claim.

**Worktree discipline, third time today.** A peer deployed `d46223a` while this
was in progress and reported that the shared tree's `session.mjs` differed from
the box — that difference was this unfinished work. Deploying from the working
tree would have shipped a half-written feature onto a live service. They
deployed from a clean worktree, so it did not.
